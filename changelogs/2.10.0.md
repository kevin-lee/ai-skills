## New Feature

### Add installation and update tracking for named Git branches (#162)

#### Before This Release

`install` always cloned whatever the repository's default branch happened to be. There was no way to install a skill from a topic branch, a release branch, or any other named branch, so a skill that only existed on a branch could not be installed at all without cloning the repo by hand and installing from a local directory. `.aiskills.json` had nowhere to record a branch either, so even a manual workaround was lost on the next `aiskills update`.

#### After This Release

`install` accepts `--branch` for Git sources, records the selection in `.aiskills.json`, and `update` keeps following it.

```bash
aiskills install owner/repo --branch develop
aiskills install owner/repo/skills/my-skill --branch feature/new-skill
```

Branch names containing `/` work, and the option also applies to full Git repository addresses (https and ssh).

```
Installing from: owner/repo (branch: develop)
  ⠋ Cloning repository (branch: develop)...
```

**Validation**

The branch name is checked before anything is cloned:

* `--branch` with a local directory source is rejected - it is only meaningful for Git sources.
* The name goes through `git check-ref-format --branch`, and reflog syntax (`@{`) and empty names are rejected outright.
* The branch is looked up on the remote with `git ls-remote --exit-code --refs refs/heads/<branch>` before the clone runs, so a missing branch is reported as a missing branch rather than as a generic clone failure. `--branch` selects branches only - a tag or a commit id is reported as missing.
* After the clone, `HEAD` is verified to be on the requested branch, so a clone that quietly landed elsewhere is treated as a failure rather than being installed.

The branch lookup runs inside the existing authentication fallback chain (`anonymous`, `ssh`, `gh`, `credential-helper`, `interactive`), so a private repository is probed with the same method that will do the clone.

**Updates**

`update` now groups installed skills by repository **and** branch, so two skills from the same repository tracking different branches are cloned separately instead of both being updated from one clone.

When Git confirms that a recorded branch is gone, an interactive `update` offers a choice:

```
Repository: https://github.com/owner/repo
  my-skill (Claude, global): ~/.claude/skills/my-skill
? Branch 'develop' no longer exists. Switch these installations to the repository's default branch for this and future updates? ›
  ‣ Keep branch - skip these updates
    Switch to default branch
```

* The prompt appears only when Git actually confirms the branch is missing. Authentication and network failures are reported as clone failures and never trigger a switch.
* Without terminal input (piped or CI runs), the affected updates are skipped and the branch selection is retained.
* Declining, or interrupting the prompt with Ctrl-C, also keeps the selection.
* Accepting clears the recorded branch only for the skills that were actually updated from the default branch.

Retained branches and failed updates are counted in the summary and listed separately:

```
Summary: 2 updated, 1 skipped (3 total)
Missing branch - selection retained (1): my-skill
```

To go back to default-branch tracking while the named branch still exists, reinstall without `--branch` and choose to overwrite the existing skill. Skipping the overwrite keeps the existing selection.

**Notes**

* `.aiskills.json` gains an optional `branch` field. Metadata without it means default-branch tracking, so existing installations need no migration.
* Switching to the default branch changes local tracking metadata only. It never deletes a remote branch.

## Bug Fixed

### Fixed: Completed `update` messages were erased by the spinner (#162)

#### Before This Release

The spinner cleared its line using a fixed assumed width. On a terminal narrower than that assumption, a completed message that wrapped onto more than one line was only partly erased, and on a wider one the spinner overwrote lines that were already printed, so `✅ Updated: ...` lines scrolled away or came out mangled.

#### After This Release

Spinner output is measured against the real terminal width, read from the `stderr` file descriptor through a new `aiskills_get_stderr_terminal_width` native call, and re-read on every render so a mid-run resize is picked up. The last known width is kept when a read fails, and the spinner disables itself outright when no width is available or `stderr` is not a TTY, so redirected output stays clean.

`search` uses the same spinner, so its output benefits from the same fix.

***

### Fixed: A failed `update` could leave a skill directory destroyed (#162)

#### Before This Release

`update` copied the new version over the installed skill directory in place. When the copy, the rename reapplication, or the metadata write failed partway through, the installed skill was left in a half-updated state with no way back.

#### After This Release

A Git update is now staged next to the target first. The new version is copied, renamed and given its metadata in a temporary staging directory, and only then swapped into place. If the swap fails, the backup is moved back, and the outcome is reported precisely:

```
Skipped: my-skill (Replacement failed: ...)
```

If even the rollback fails, the message names the backup path so the installation can be recovered by hand. Staging directories are removed in every case except that one.

## Internal Housekeeping

### Derive the project version from the git tag with `sbt-dynver` (#160)

`version.sbt` is gone. The project version now comes from the git tag via `sbt-dynver`, so a release no longer needs a version bump commit and a `[skip ci]` reset commit around it.

* Added `sbt-dynver` `5.1.1` and set `ThisBuild / dynverSonatypeSnapshots := true`.
* Every workflow that builds the project checks out with `fetch-depth: 0`, since `sbt-dynver` needs the tag history.
* The release workflow's `release-version-check` job becomes `release-precheck` and now verifies three things instead of comparing `version.sbt` against the tag:
  * the tag matches `vMAJOR.MINOR.PATCH` with an optional suffix,
  * the tag points at `HEAD`, so `sbt-dynver` derives exactly that version,
  * `changelogs/<version>.md` exists on the tagged commit and is not empty.

***

* Bumped `actions/setup-java` from `5` to `6` across the build, checks, and release workflows
